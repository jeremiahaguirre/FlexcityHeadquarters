## Tenancy and isolation

Every tenant-scoped table has a `tenantId` column. Postgres row-level security (`apps/api/db/rls.sql`) compares it with `app.tenant_id`, which the API sets at the start of every transaction (`withTenant()` in `src/lib/db.ts`).

- The API connects as `flexcity_app`, which is **not** the table owner, so RLS always applies (`FORCE ROW LEVEL SECURITY` as well).
- With no tenant set, every policy evaluates to false: a forgotten context returns **no rows**, never all rows.
- `flexcity_app` has no `DELETE` on payroll-bearing tables, and audit logs are append-only.
- The tenant is resolved from the request's subdomain before login through a `SECURITY DEFINER` function that exposes only public branding fields. Access tokens must belong to the same tenant as the subdomain.

## Roles vs. positions

The original single `role` field conflated *what you may do in the app* with *what you may work*:

- **AccessRole** (many per user): HR_ADMIN, AQUATIC_SUPERVISOR, HEAD_LIFEGUARD, STAFF, FRONT_DESK, UNION_STEWARD, EMPLOYEE (general city staff: water works, parks…). These map to permissions in `src/auth/permissions.ts`; routes check permissions, never role names.
- **Position** (tenant-defined: Lifeguard, Swim Instructor…): what a shift requires. Positions require certifications, and certifications can require others (National Lifeguard requires current first aid). A manager approves each user for each position.

## Time

- All instants are `timestamptz`. Local reasoning (work days, pay weeks, availability, school hours) always uses the facility's IANA timezone.
- Employment-standards province is on the **facility**, not the tenant.
- The API sends facility-local timestamps for display, so browsers with stale timezone data can't show different times. (This is a live issue: tzdata 2026e keeps BC on UTC−7 year-round.)

## Key flows

### Eligibility (`services/scheduling/eligibility.ts`)

A pure function decides whether a person may work a shift and explains every refusal. The database loader does coarse filtering in SQL; the pure function makes the final decision. The Shift Board, the scheduling assistant, Fill the schedule (run and accept), the schedule builder’s drag and drop, copy and assign-many, trades, storm call-outs and supervisor approvals all use the same function, with the same inputs (`evalOpts()`): the province's rules (or the federal set for a federally regulated organization or department), the school calendar and the organization's (or department's) **limits**, so one rule set applies everywhere:

- certifications valid through the shift's own date; position, onboarding, age (a missing date of birth is a warning flag everywhere: proposals, planner status, manual assign); time off; availability in wall-clock minutes (DST-correct, windows past midnight, a shift after midnight against the previous day's late window);
- rest between shifts; **daily rest** measured in every 24 hours that start at a shift start (Ontario's 11 h; rest may cross midnight); **weekly rest** as the longest time off in a row inside each pay week the shift touches (BC/QC 32 h, ON 24 h or 48 h over a fixed pair of weeks, others per `provincialRules.ts`);
- **max hours a day**: the shift's own length and the total in the province's "day" (a calendar day, or in BC/AB the 24 hours from the start of a shift past midnight, `compliance/workDay.ts`, shared with payroll's daily overtime); **max days in a row** (each shift counts on its start date), capped at 12 by weekly rest;
- the personal weekly cap and work restrictions in every pay week the shift touches; hours of service; young workers; overtime projected with the payroll engine.

Each refusal is refused only when the shift causes or worsens it (an existing shortfall isn't blamed on the next shift). Every write that assigns takes advisory locks first, shifts then people in sorted order (`scheduling/locks.ts`), so two departments can't both book a person they share; overtime charged to the ledger is reversed (a negative entry) when the assignment is undone, unassigned, reassigned, traded, given away on the board or cancelled.

### Fill the schedule (`services/scheduling/solver.ts`, `fillRun.ts`, `solverSettings.ts`)

A pure, seeded solver assigns people to a week's open draft shifts; the web runs a horizon (1, 2, 4 or 13 weeks) one week at a time, sending each week's proposals forward so hours, weekends and evenings balance across the horizon.

1. **Static screen** per person and shift: position held, certifications verified and valid through the shift (with prerequisites), blocking onboarding, minimum age, time off, availability, work restrictions. It only removes people the full check would refuse.
2. **Greedy**, hardest shift first (fewest qualified people, then earliest), each to whoever raises the weighted cost least; ties go to fewest hours so far, then a seeded order (never names or hire dates).
3. **Local search** (simulated annealing): reassign, swap, and move-and-back-fill to open a slot. It stops at an iteration budget, scaled down for large runs (min(250 000, 300 per shift, 4 000 000 ÷ people)), so a seed reproduces the run, or at the time budget (≤ 3 s a week). When the clock ends it, the summary and the audit row say `reproducible: false`: the same seed may then give a different answer.
4. **Verification**: every proposal is re-checked with `evaluateCandidate()` and the organization's limits against all of that person's other shifts (published and drafts, any department, each in its own facility's time zone), plus travel time (an organization setting), and no overtime unless allowed. Anything refused is dropped and re-tried. The fast model in steps 2–3 mirrors the same rules (true shift length, BC/AB overnight day, daily and weekly rest, days in a row) so verification rarely drops anything.
5. **Explanations**: reasons per proposal and three alternatives; for open shifts, how many hold the position and what stops each.

Cost, lowest first: an open shift (1000), short required coverage (per hour; certificates checked on each window's own date, windows past midnight included), then weighted (0–10) contracted hours with tiers (full-time, then part-time, then casual and on-call; full-time staff aim at the department's or the organization's full-time weekly hours), fair hours (squared hours above target across the horizon), labour cost (overtime at 1.5, BC double time past 12 h at 2.0, statutory-holiday hours at the province's multiplier (NL 2.0), shift premiums) and the overtime ledger, weekends/evenings/holidays rotation, continuity, main position and confirmed availability, and seniority only when the organization's switch and the department allow it (otherwise it is never read; the same department switch applies to the overtime order and call-outs). Weights, toggles, limits and the **Plan ahead** window live in `Tenant.overtimePolicy.solver`, with per-department overrides; the plan-ahead window is both how far ahead staff confirm availability (confirmations are `availability.confirm`/`availability.update` audit rows) and the default horizon, and later weeks are tentative.

A run is read-only apart from its audit row. Shifts the forecast suggests (at least the organization's minimum shift length, default 3 h; nothing on statutory holidays at facilities marked closed) are a preview: proposed like open drafts (`new:` slots) and created only when accepted. Accepting runs one transaction per pay week, takes the shift and person locks, re-checks each proposal with the full rule set (eligibility with limits, availability, travel, overtime), writes draft assignments with a compare-and-set on `Shift.version` and charges accepted overtime to the ledger; each week's audit row is an undo token, and the browser keeps a stack (undo takes back the latest accept). Undo re-checks who it restores (someone who can no longer work it leaves the shift open), cancels shifts the accept created and reverses the overtime charge. Publishing first runs a check (`POST /shifts/publish/check`): required-coverage gaps the schedule would leave, assigned drafts someone can no longer work (e.g. a certificate lapsed) and, for federally regulated work, shifts inside 96 hours' notice; with any of these, `POST /shifts/publish` refuses (`PUBLISH_WARNINGS`) unless `acknowledgeWarnings` is sent, which is audited (`shift.publish.warnings_acknowledged`). A run covers one department's positions (or all the person schedules), proposes only people in the person's scope who hold one of those positions, and never touches published shifts.

### Scheduling by hand (`services/scheduling/planner.ts`, `routes/planner.ts`, web `components/planner/`, `lib/planner.ts`)

The schedule builder's month, week and day views put a people panel beside the schedule. Drag and drop is plain pointer events (mouse and pen; no library): the ghost moves through a ref, targets are found with `elementFromPoint` and `data-drop` attributes, and the pointer math (15-minute snapping, lanes, period math) is pure and unit-tested. Touch screens and keyboards don't drag: a shift opens a ranked list of people, or a picked person is placed on a shift or a day. Screen readers hear the drag, each target's verdict and the result through a live region.

- **Board** (`GET /schedule/planner`): the department's people (scope and department as in Fill the schedule, people from other departments marked), each with availability (a window past midnight shows on the next morning too) and approved time off per visible day, hours in the period (every department; for a single day, the pay week around it) against their target, and Plan-ahead confirmation; the shifts; each position's usual start–end times (last 4 weeks) to prefill a new shift.
- **Batch eligibility** (`POST /schedule/planner/eligibility`): `evaluateCandidate()` for every person × shift in the period (only people who hold the position; identical shifts once per person) and for a typical new shift per person × day. Blocks are refusals; overtime, flags and being outside submitted availability are warnings (assigning by hand doesn't require availability; overtime asks for confirmation). People are referenced by index and each distinct list of reasons is sent once. The browser asks in chunks of 20 people in the panel's order (two at a time), asks for a dragged person first, and after a change re-asks only for the people and shifts it touched. The browser never decides: it colours what the API returned, and every drop is re-checked on write.
- **Writes**: create with people (`POST /schedule/planner/shifts`, one draft each, all or nothing), move/resize/reassign/copy (`POST /schedule/planner/shifts/:id/move`, through `updateShift()` and `assignShift()`, so hard rules refuse and new overtime needs confirming), several people on one shift (`assign-many`: the shift plus a same-time draft for each other person), copy a day or week (`/copy`, wall-clock times kept across daylight saving, each person re-checked in order and kept only without overtime, never copied twice) and cancel drafts (`/cancel`, for undo). Shift edits are audited as before; copying adds a `schedule.copy` row. Undo/redo is the browser's own stack of these calls.

Speed: time-zone conversions in `lib/time.ts` remember recent answers and batch checks share a person's existing overtime per pay period; a month for 300 people and 420 shifts checks in about 5 s in the background (one person: under 0.2 s; a refresh after a change: about 0.1 s).

### Work rules, rotations and on call (`services/scheduling/workRules.ts`, `rotations.ts`, `onCall.ts`, `changeNotice.ts`, `twoPerson.ts`, `shiftWarnings.ts`, `services/payroll/workRulePay.ts`)

Settings live in `Tenant.workRules` (breaks, call-in minimum, notice, standby, premium rules; `departments` overrides), read with `parseWorkRules`/`effectiveWorkRules`; the department's limits and federal switch stay in the Fill settings (`overtimePolicy.solver.departments`), edited on the same Work rules screen.

- **Paid hours.** `breakMinutesOf(shift, position)` (the shift's own break, else the position's on shifts over 5 h) and `paidIntervals()` carve the unpaid break out of a shift. `calculatePay` does it for any interval carrying `breakMinutes`/`breakAt`, so payroll, the pay preview and `projectOvertime` (Shift Board, planner, assign, Fill verification) agree; the solver's fast model splits pieces the same way. Rest, overlap and shift-length checks still use the whole shift.
- **Payroll** (`workRulePay.ts`): breaks taken out of single punches that cover the planned window; rule premiums through `calculatePay`'s `rulePremiums` callback; `REPORTING_PAY`/`CALLBACK_PAY` top-ups per scheduled shift; `SCHEDULE_CHANGE_PREMIUM` from `ShiftChange` rows with `payOn` in the period; `STANDBY_PAY` from `OnCallPeriod`. Each line adds vacation pay.
- **Change notice**: `updateShift`, `assignShift` and `cancelShift` call `recordShiftChange()` for published shifts (planner moves go through them); `POST /shifts/:id/change-preview` gives the web the same answer before saving.
- **Two-person minimum**: `twoPersonViolations()` (pure) is used by the solver (a soft coverage need, then a hard pass that leaves a lone never-alone shift open with `TWO_PERSON`), by `shiftWarnings()` (planner board) and by `publishCheck()` (a confirmation to publish).
- **Rotations**: `RotationTemplate` (cycle days, anchor date, pattern of days with wall-clock times, crews with offsets, people and open slots). `generateFromTemplates()` makes drafts (`rotationTemplateId`), wall-clock per date (DST), skipping statutory holidays at facilities closed on them, idempotent; crew members are placed only when `evaluateCandidate()` passes without overtime and the date is inside the plan-ahead window, otherwise the shift stays open with the reason for Fill or the planner. Routes in `routes/rotations.ts`; the planner's Templates action and Fill's "Start from rotation templates" call it.
- **On call**: `OnCallPeriod` per department; rotate, swap/reassign (both notified), call-backs (`callBack` shifts, rule-checked, emergency override audited, short rest before the next shift flagged). `onCallAt()` puts the person on call first in winter call-out lists and first among working-alone escalation contacts.

### Weekly shift templates and shift preferences (`services/scheduling/shiftTemplates.ts`, `preferences.ts`, `routes/shiftTemplates.ts`, `routes/preferences.ts`, web `components/scheduling/ShiftTemplates.tsx`, `Preferences.tsx`)

- **Templates** (`ShiftTemplate`, `ShiftTemplateSlot`): a department's standard week, optionally bounded by dates (Summer, School year). Each line is weekdays × start/end (minutes; an end past 1440 runs past midnight) × position × facility × headcount × unpaid break. `applyTemplate()` makes DRAFT shifts for `[from, to)` (≤ 13 weeks), wall-clock per date in the facility's zone, tagged `templateSlotId` and `templateApplicationId`. Idempotent: occurrences already made by the same line (not cancelled) count against its headcount, so re-applying makes nothing and a longer range adds only the missing days; editing a template keeps the ids of unchanged lines. Closures: statutory holidays at facilities in the Fill settings' holiday-closed list are skipped (`HOLIDAY_CLOSED`); a facility with opening hours (`FacilityHours`) and none that weekday is skipped (`FACILITY_CLOSED`); a line outside the day's hours is made and flagged (`OUTSIDE_HOURS`, also written to `conflictReason`); a holiday at an open facility is made and flagged (`STAT_HOLIDAY`). Every application is a `ShiftTemplateApplication` row; undo cancels its drafts still in DRAFT (reversing overtime they carried) and keeps published ones. With `overtimePolicy.solver.templateAutoCreate` on (off by default; `tenant.configure`), the hourly worker job `shift-templates` applies each active template with `autoWeeksAhead` > 0 to its next weeks (automatic applications have no `createdById`). Permission `schedule.templates`, department scope as in Fill the schedule (every line must be in the person's scope); feature `shiftTemplates`. Live topic `templates`.
- **Preferences** (`ShiftPreference`, `ShiftPreferenceLimit`): prefer/avoid windows (weekdays, a start-time window, position, facility, a note) and the most hours or days a week the person would like. Not availability: availability stays a hard rule; preferences are soft. The solver scores each person × slot (+1 preferred, −1 avoided; avoid wins) and adds, under the `preferences` weight, 3 per avoided shift, 1 per shift outside a stated preference, −1.5 per preferred shift, 0.3 × (hours over their preferred weekly hours)² and 4 per day over their preferred days — small next to an open shift (1000), so no shift is left open for a preference and no hard rule, overtime limit, fairness or seniority term is bypassed. Reasons `PREFERENCE_MET`, `PREFERENCE_AVOIDED`, `PREFERENCE_OUTSIDE`, `PREFERENCE_OVER_HOURS`, `PREFERENCE_OVER_DAYS`. The planner board returns them per person. Privacy: `preferences.self` for one's own (`/me/preferences`); `/users/:id/preferences` and the planner only for `schedule.write` holders whose scope includes the person (HR doesn't see them); the audit row keeps counts only; included in the records export; deleted on anonymization and by retention 90 days after someone who left last changed them. Feature `shiftPreferences`.

### Team messaging (`services/messaging/`, `routes/messages.ts`, web `components/messages/`, `lib/messages.ts`)

- **Conversations** (`Conversation`, `ConversationMember`): one to one (`directKey`, one per pair), a shift's (`shiftKey`: everyone on published shifts overlapping it at the facility; read-only `shiftArchiveHours`, default 12, after it ends; people added to the shift join when it's opened again; a lead whose department has the shift may join), a department's (its people and managers only, kept in step each time it's opened) and groups a lead or HR makes (`messages.groups`; the maker is the owner and adds or removes people). HR who isn't on the shift or in the department can't join (`403`); they open it for an investigation. Anyone added after a conversation was made gets `ConversationMember.historyFrom` and sees only messages sent from then on, enforced on the server in `readConversation`, unread counts, files, push previews and their records export; joining a conversation someone else made is audited (`messages.join`).
- **Who can message whom** (`policy.ts` `canReach`): never across organizations (RLS); HR reaches anyone and anyone reaches HR; leads reach the people they lead and back (reports-to, departments they manage, supervisor roles in their department); staff reach colleagues in their own departments while `staffDirect` is on (default). No departments yet = one department. Checked when a conversation is made and on every message.
- **Rule of two** (`directSafe`, `groupSafe`): a minor never has a one-to-one conversation with an adult, whatever the adult's role; minor-to-minor one to one unless the organization turns `minorDirect` off; a group with a minor (or an unknown age) needs two adults or turns read-only. Minor = younger than the age of majority (`services/legal/ages.ts`: 19 in BC, NB, NL, NS, NT, NU, YT, 18 elsewhere; the highest of the organization's facilities' provinces). No birth date on file = possibly a minor (the app has no other proof of age), unless HR has confirmed on the person's record that they are of the age of majority or older (`User.adultConfirmedAt/ById/Note`, `services/people/adultConfirmation.ts`, `PUT/DELETE /users/:id/adult-confirmation`, `users.write` only; a short note of how is required, e.g. "ID checked at hire"; audited `user.adult_confirmed` / `user.adult_confirmation_removed`; shown only on HR's view of the person, next to the birth date; in the records export; cleared on anonymization). A birth date always wins: `ageClass()` uses the confirmation only when there is no birth date, and HR can't confirm someone whose birth date says minor (`409 BIRTH_DATE_MINOR`). Evaluated live, so a birthday or a corrected birth date lifts or applies it at once; a conversation it blocks is kept, read-only. The directory (`GET /messages/people`) leaves out anyone you can't message one to one, with no flag (the screen says some one-to-ones aren't available); opening one directly is still `403 MINOR_RULE`. A read-only conversation's reason (`readOnly`) is given only to HR; everyone else gets `readOnly` (or `archived` for a closed shift conversation, which is about time, not people), and sending into a group the rule of two blocks is `409 READ_ONLY` for them. Refusals are `403 MINOR_RULE` with the same words whoever asks, never an age, and are audited as `messages.blocked` `{ rule: 'minor rule', what }` in their own transaction (`inMessaging`).
- **Sealing** (`crypto.ts`): each conversation has a data key wrapped by the organization's KMS key; message text, the first version of an edited message, files and file names (`MessageAttachment.nameCiphertext`; rows from before are sealed by the retention run, which clears the old `fileName`) are AES-256-GCM with an AAD naming organization, conversation, message and part. No fingerprint of files is kept (nothing used it). One unwrap per request, not per message. **No server-side search** of message text (it would need the text unsealed or indexed); people find conversations by name, and the browser can search what it shows.
- **Messages**: text up to 2,000 characters, an optional file through the documents' checks (`lib/files.ts`: PDF/PNG/JPEG/WebP sniffed, renamed, 10 MB, sent with `sendFile`). The author edits within 15 minutes (the first version is kept, sealed) and removes any time ("message removed"; the sealed text stays for an investigation until retention ends). Read receipts are each member's `lastReadAt`; unread counts (muted conversations excluded) feed the menu badge.
- **Live and notifications**: writes call `announceChangeTo(tx, tenant, 'messages', memberIds)` (lib/changes.ts: a pg_notify carrying the organization, the topic and who to tell, never content); `liveHub` sends `event: change` only to those people's streams. One `message_new` notification per conversation until read (`{ conversationId, messageId, from }`: never message text); the push says "New message from X", and with `pushPreview` on, its first 60 characters, made from the sealed message when the push is sent (`messagePreviews`; none if the message was removed or the person can't see it). Removing a message deletes the notifications pointing at it; so does erasing its author. Muted conversations don't notify. Messages say they aren't for emergencies and link the working-alone help button.
- **Reports and investigations**: any member reports a message (`MessageReport`; HR is notified `message_reported`). HR (`messages.investigate`) reads a conversation it isn't in only after `POST /messages-admin/conversations/:id/investigate` with a reason (≥ 10 characters): an append-only `ConversationAccess` for 14 days; the opening, every reading and every file opened are audited (`messages.investigation_open`, `_read`, `_file`), and looking up someone's conversations (names and members only, `POST /messages-admin/people/:id/conversations`) needs a reason too and is audited with it (`messages.investigation_lookup`). One report per message per person, open or closed. An investigation reads removed and edited messages; it can't write.
- **Rate limits** (`auth/rateLimit.ts` `allow`, per person; `LIMITS` in `conversations.ts`): 30 messages a minute and 600 a day, 20 files an hour (and the 14 MB request limit), 20 new conversations or groups an hour, 10 reports an hour; `429 TOO_MANY`. Survey answers: 30 an hour per person (one per invitation already).
- **Privacy**: retention `messagesDays` (default 730, 180–3650) after a conversation's last message, except while a report on it is open (held conversations are excluded before the batch, oldest first); in conversations still in use, a removed message's sealed text and file go once the period has passed since it was removed, and an edit's first version once it has passed since the edit (unless under an open report). Anonymization wipes what the person wrote (except under an open report), deletes the notifications pointing at it and removes them from every conversation; the person's records export has the text of messages they wrote, with their own first versions (others' messages counted only, from when they could see them). The organization export, while it is active, has conversation metadata only (`Conversation` rows with `memberIds` and `messages`, `ConversationMember`; no `Message` or `MessageAttachment`, no previews); message text, first versions and files are included only once the organization is offboarded (the export it receives as it leaves, when the records pass to it), audited `data.export_messages` `{ messagesIncluded: true }`.

### Staff surveys (`services/surveys/`, `routes/surveys.ts`, web `components/surveys/`, `lib/surveys.ts`)

- **Kinds**: pulse check-ins (always anonymous) and exit surveys (one person from an open `Offboarding`, always named, and the person is told before answering; HR only). Questions: rating 1–5, one choice, several choices, short text (≤ 20 questions). HR (`surveys.manage`) surveys anyone; managers (`surveys.department`) only when the organization turns `managersCreate` on, and only their departments. Repeating a pulse keeps its `seriesId` for the trend.
- **Anonymity**: who was asked and whether they answered (`SurveyInvite`: person, survey, a yes/no; no time) is kept apart from the answers (`SurveyResponse`: no person, no time, random id; the app can't update it). Each survey has one breakdown (`Survey.breakdown`: `NONE`, `DEPARTMENT` (default) or `POSITION`), chosen in the editor and fixed once sent; a response keeps only that group, and only where it reaches the minimum group among those asked. Two breakdowns suppressed separately could be subtracted (a department minus a position in it can leave one answer), so results, the CSV, the trend and the organization export use only the survey's own (existing surveys kept the department; their position tags were cleared). Managers reach their own surveys only while `managersCreate` is on and they still manage every department the survey covers; otherwise only HR. An anonymous survey can't be sent to fewer people than the minimum group. Results open only once it closes (watching numbers move would reveal each answer) and only for ≥ `minGroup` responses (default 5; organization can raise it, never below 3; fixed when sent). Breakdowns hide groups under the minimum and then enough of the smallest shown groups that the hidden ones reach it too (complementary suppression, `showableGroups`); written answers only in the overall view, alphabetically, with a warning; the CSV has summaries and sorted written answers, never one row per person. HR and managers see counts, never who. Limit: someone with raw database access could try to match the two tables by transaction ids; nothing the app shows or exports exposes them.
- **From offboarding and Today**: HR's offboarding screen has "Send exit survey" for each open offboarding (shown only with `surveys.manage`, so only while the feature is on), which opens the survey editor at `/manage/surveys?exit=<offboarding>` as an exit survey for that person with starter questions (no templates). Staff's Today screen shows a calm card for the open, unanswered survey closing soonest ("A short survey from HR · closes …"), hidden for the session when dismissed. The live topic `surveys` (sent to those asked on publish, to the person on answering, to the organization on close) refreshes it.
- **Reminders**: at most two per survey (a button, and an hourly job sends one a day before closing if none was sent), only to those who haven't answered, never once closed.
- **Privacy**: retention `surveysDays` (default 730) after a survey closes, with its invitations and answers; anonymization deletes the person's invitations and named answers; the records export lists surveys asked, whether answered, and named answers; the organization export writes anonymous surveys as threshold-respecting results only (`surveys/<id>-results.json`), named answers as rows.

### Shift bidding by seniority (`services/scheduling/bidding.ts`, `routes/bidding.ts`, web `components/bidding/`)

Feature `shiftBidding` (off by default) declares `requires: 'seniority'` in `features.ts`: the organization's effective switches (`tenantSettings`, `withRequirements`) turn it off whenever seniority is off, so its permissions, menus and routes go too (the routes also `requireFeature('seniority')`), and the Dev console shows "Needs seniority". A department whose Fill settings turn seniority off can't hold a round (409 `SENIORITY_OFF`).

- **Rounds** (`BidRound`, `BidItem`): open draft shifts of chosen positions (by ids or dates), or LINES: the template is applied over the range first (idempotent), then `buildLines()` makes one item per seat of each template line (the k-th draft of that line on each date, by id), covering the whole season. Shifts in an unfinished round can't go in another; every item must start after the close. Basis per round: `DATE` (seniority date, then hours) or `HOURS` (hours, then date); default `overtimePolicy.solver.bidSeniorityBasis`.
- **Ranking** (`BidChoice`): people holding a round position replace their ranking while it's open (positions they hold only); they see their own place in the live order, never anyone else's choices.
- **Close** (worker `bid-rounds`, every minute; it also notifies eligible staff once a round opens): `seniorityOrder()` (basis, then hire date, then `tiebreakOf()` = SHA-256 of round and person, recorded on `BidEntrant`), then `awardBids()` in the round's `awardOrder` (`BidAwardOrder`; the organization default is `solver.bidAwardOrder` in `overtimePolicy`, set with `PUT /bids/settings`; a round can choose its own): `ROUND_ROBIN` ("one at a time, in seniority order", the default) — pass p gives each person (most senior first) with fewer than p awards their highest-ranked choice still open that passes the check; `SENIOR_FIRST` ("most senior first takes all their awards") — each person in order gets up to `maxAwardsPerPerson` of their ranked choices before the next person (an award's `pass` is then its number in that person's turn). Both stop at `maxAwardsPerPerson`; with 1 they give the same result. Staff's "How awarding works", the steward view and the award reasons say which order the round used. The check is `evaluateCandidate()` with the Shift Board's options (no availability requirement) against the person's shifts plus what they won in this round, every shift of a line in turn, no overtime, travel time. Each choice's outcome is stored: `AWARDED`, `TAKEN_BY_SENIOR`, `TAKEN_EARLIER_PASS`, `NOT_ELIGIBLE` (+ rule code), `LIMIT_REACHED`, later `OVERRIDDEN` or `CHANGED`. Status → `REVIEW`; managers notified.
- **Review**: `bidding.manage` (department scope) may give an item to someone else or nobody with a required reason; the new person must pass the same check; audited (`bid.award.override`).
- **Who**: supervisors and custom lead roles have `bidding.manage` for their departments; HR administrators have it organization-wide and, with `tenant.configure`, set the organization's defaults (seniority basis, award order) through `PUT /bids/settings`.
- **Confirm**: under `lockForAssignment` each award's shifts are re-checked (still open drafts, eligible, no overtime) and assigned + published with a compare-and-set on `version`, otherwise dropped (`CHANGED`); every other shift of the round is published and posted on the Shift Board (`postOffer`, its usual notifications); everyone who bid gets `bid_awarded`/`bid_not_awarded`. Live topic `bids`.
- **Union stewards**: `bidding.observe` (UNION_STEWARD role) reads rounds in REVIEW or AWARDED: the order with seniority snapshot, outcomes, override reasons. This is in the main app, not the Union Hub service (whose database role can't read scheduling tables); the steward role already sees the seniority roster.

### Shift Board (`services/shiftboard/offers.ts`)

```
post (holder or supervisor) ──► OPEN ──claim──► eligible, no OT ──► COMPLETED (shift reassigned)
                                  ▲               │
                                  │               └─ OT ──► PENDING_APPROVAL ──approve (re-checked)──► COMPLETED
                                  └──────────────────────────────────── deny ◄─┘
```

- The original holder stays assigned until COMPLETED.
- Claims take advisory locks on the shift and then the claimant (fixed order, no deadlocks), and the reassignment is a compare-and-set on `Shift.version`.
- Only eligible staff are notified when a shift is posted.

### Pay (`services/payroll/payCalc.ts`)

Punches are split at local midnight and grouped into work days. Daily thresholds are applied, then weekly thresholds per pay week, using the province's method ('stacked' never counts daily-OT hours toward the weekly threshold; Alberta pays the greater of daily or weekly OT). Rates are looked up per position and date. Money uses decimal arithmetic. The Shift Board's overtime warning calls the same engine, so the warning and the pay stub can't disagree.

### Payroll runs (`services/payroll/payRuns.ts`)

A regular run takes the period's approved hours from the pay engine, adds salaried staff (the annual
amount ÷ pay periods, prorated by days), and works out each statement: CPP/QPP, EI, QPIP and income
tax by the T4127 method, benefits and union dues, then the run's one-time items (bonuses, retro pay
and vacation payouts by the bonus method in `lumpSum.ts`; allowances; untaxed reimbursements; after-
tax recoveries) and court or CRA orders, capped by their share of net and what's still owed.
Off-cycle runs carry only their one-time items. A second person approves; the deposit file
(CPA-005) goes to the city's bank over SFTP or by download. With a payroll provider instead
(`providers.ts`), each period's approved hours go to ADP, Dayforce or Wagepoint over their API.

### Operations

Chemical readings are checked against each pool's configured thresholds; there are no built-in defaults. Out-of-range readings **recommend** closure, and a Head Lifeguard or Supervisor confirms or dismisses with a note.

### Demand forecast (`services/ops/forecast.ts`, `weather.ts`, `specialEvents.ts`)

Expected attendance per hour comes from the facility's own headcounts, its opening hours and lesson registrations, then is adjusted per day for the weather, statutory holidays (the payroll holiday table), school breaks (the school calendar) and special events (per facility or city, extra people, a percentage or both, optionally yearly). Weather is Environment and Climate Change Canada open data (MSC GeoMet, `api.weather.gc.ca`, no key), fetched by the worker for each distinct forecast site and cached in tables shared by every city with no organization's data in them ([SUBPROCESSORS.md](SUBPROCESSORS.md)). The weather's effect is a rule of thumb per kind of facility until it is learned from the facility's own counts against observed weather. Every adjustment carries its reason, the unadjusted figures are kept, and the forecast works without weather (and says so). The parser was written against the documented format with recorded fixtures; the first live fetch is still to be checked ([roadmap](ROADMAP.md#next)).

### Reporting lines (`services/people/reporting.ts`)

`User.reportsToId` (same organization, never oneself or someone below; changes audited), defaulting to the department's managers. Requests (time off, expenses, trades, overtime claims) notify the manager first, then the department's managers, then everyone holding the permission; queues take `?team=mine`. Routing only: a manager is told about, or can act on, a request only when their permissions and department scope already allow it.

### Offline punches (`services/timeclock/punches.ts`, web `lib/offlinePunches.ts`)

Without a connection the web app keeps each punch on the phone, per person, with its own id and the time it happened, and sends the queue in order when the connection returns. The server recognises a re-sent id (never a double punch), corrects for the phone's clock difference, refuses future, out-of-order or more-than-3-days-old punches with a reason, and flags the rest "Recorded offline" for review, with when each part arrived.

## Sensitive data

| Data | Protection |
| --- | --- |
| Incident narratives | AES-256-GCM per record; data key wrapped by the tenant's KMS key; bound to the record with AAD; every read logged with a purpose |
| Union messages | Separate schema and DB role; sealed with the union local's own key |
| SIN, bank accounts, provider and bank credentials | Sealed with the city's own key (envelope encryption, AAD-bound); a SIN is unsealed only into a filing file, with a passkey, and audited |
| Signed agreements | The application role can't update them; fingerprints of the text and signature are re-checked on each certificate |
| Refresh tokens | Stored as SHA-256 hashes; reuse of a rotated token revokes the whole family |
| Calendar feed links, kiosk secrets | Only a SHA-256 hash of each secret is stored; the link or set-up address is shown once |
| Kiosk PINs | Hashed with scrypt like passwords; easy PINs refused |
| Text-message codes | 6 digits, 10 minutes, stored as an HMAC keyed with the server secret (a plain hash of 6 digits could be reversed) |
| Résumés, receipts, T4A payees' SINs | Sealed with the city's own key like other documents and SINs; each résumé download is audited |

| Location | At punch time, only whether the person was on site and how far; during a working-alone session the person shares, the latest position only |
| SQL | Values are always bound parameters; identifiers only through `ident()`; a test fails the build on SQL built from values; runtime roles can't change the schema (see [SECURITY.md](../SECURITY.md)) |

## Events

Nothing a change causes is kept only in memory, so a process that stops at the wrong moment loses nothing.

- **Direct notifications.** A feature that knows its recipients calls `notify(tx, …)` inside its own transaction: the in-app notification, and any email (`EmailOutbox`), text or call (`SmsOutbox`), commit together with the change, or not at all. Working-alone reminders, escalations and calls for help (`services/safety/loneWork.ts`), winter call-outs (`services/winter/callOuts.ts`) and the rest work this way.
- **Domain events** (`src/lib/events.ts`): shift-board offers posted, claimed, approved or denied, time off decided, pool readings out of range, front-desk pages, and drafts from scheduling. A service returns its events; the route records them with `recordEvents(tx, …)` / `withEvents(tx, …)` **in the same transaction** as the change, as rows of `EventOutbox` (tenant-scoped, RLS). A rolled-back change leaves no event. Urgent open-shift texts (`shift_urgent`) come from `shift.offer.posted`, so they go through here.
- **Dispatcher** (`src/lib/outbox.ts`). Straight after the commit the route calls `dispatchSoon(tenantId)`, and the same API process delivers the event within milliseconds. `recordEvents()` also announces the organization on `fh_events` (`pg_notify`, sent only at commit), and the worker LISTENs and delivers that organization's events, then the webhooks they queued, at once: so events recorded by the worker's own jobs, or by a process that stopped first, go out without waiting. `dispatchAll()` every 30 seconds is the safety net for retries that come due (backoff) and announcements missed while the LISTEN connection was reconnecting. Each event is claimed with `SELECT … FOR UPDATE SKIP LOCKED` inside its organization's transaction, its handler (`handleDomainEvent`: notifications, emails, texts) runs in that same transaction, and the event is marked `DELIVERED` before it commits: the handler's writes and the mark commit together. Any number of dispatchers can run at once; none waits for another and none delivers an event twice. A crash mid-delivery rolls everything back and the event is delivered later: **at least once**. Notifications written for an event carry a dedupe key (`<event id>:<hash of recipient, type, params>`, unique per organization), so a second delivery adds nothing, emails and texts included.
- **Failures** roll back to a savepoint; the attempt count, the error and the next try are recorded (backoff 5 s, 10 s, 20 s … 10 min). After `EVENT_MAX_ATTEMPTS` (8) the event is `DEAD`, reported to the error reporter and counted in `outbox_backlog()` (channel `events`) for `/readyz` and `/metrics`. To retry one by hand: set its `status` back to `PENDING` and `availableAt` to now.
- **Across organizations** the worker asks `tenants_with_due_events()` (`SECURITY DEFINER`, ids only), then claims each organization's events under its own context, as other jobs do with `all_tenant_ids()`.
- **Public webhook events** (`person.*`, `shift.*`, `timeoff.*`, `punch.approved`, `payrun.approved`) are written to the same outbox by Postgres triggers (`fh_public_event` in `db/rls.sql`) in the change's own transaction, only when an enabled endpoint wants that type. The dispatcher queues one `WebhookDelivery` per endpoint; the worker sends them outside any transaction with retries and auto-disable ([PUBLIC-API.md](PUBLIC-API.md)).
- **Retention:** a delivered event's payload is cleared at once; delivered rows are deleted after 7 days, dead ones after 30 (`services/privacy/retention.ts`).

Notifications are announced with `pg_notify` inside the transaction that writes them, so Postgres delivers the signal only on commit. Browsers listen over server-sent events (`/api/notifications/stream`), and emails, texts and calls go out through the outboxes (below). Web push to phones and computers follows the same notifications (`services/notifications/push.ts`); the lock screen shows a short heading only.

### Urgent texts, calls and pushes

Working-alone reminders, escalations and calls for help, winter call-outs, urgent open-shift texts and sign-in codes leave within a second or two of the commit that queued them, not at the worker's next minute (`services/notifications/urgent.ts`).

- **Queued with the change.** `notify()` (and the code route) writes the `SmsOutbox` row in the change's transaction and calls `urgentSoon(tx, tenantId)`, which sends `pg_notify('fh_urgent', tenantId)` (delivered only on commit) and registers an `afterCommit` hook (`lib/db.ts`: runs once `withTenant()` has committed, never on a rollback). The same applies to urgent push kinds (`push.ts` `URGENT`) when web push is on.
- **Delivered at once, in-process.** `enableInlineUrgent()` (in `server.ts` and the worker) makes the hook deliver that organization's due texts and calls, then pushes, then emails. Kicks are coalesced per organization. A request for help is called and texted milliseconds after its response is committed.
- **Worker within ~1–2 s, from any process.** The worker LISTENs on `fh_urgent` (`lib/listen.ts`, `LISTEN_DATABASE_URL`) and runs the same delivery for that organization. Every 30 seconds it also asks `tenants_with_due_sms()` (`SECURITY DEFINER`, ids only) for organizations with texts due, which covers retries and a NOTIFY lost while LISTEN was reconnecting. The minute jobs (`deliverSms`, `deliverOutbox`, `deliverPush`) stay as the last backstop.
- **Never twice.** Every path claims one message at a time with `SELECT … FOR UPDATE SKIP LOCKED` in the organization's transaction (RLS), sends it while holding that row lock, and marks it sent before the commit (`sms.ts` `deliverSmsTenant`, `mailer.ts` `deliverEmailTenant`; `deliverPush` claims notifications the same way). A message another process holds is skipped. The one gap: a process that dies after the provider accepted a message but before the commit sends it again later (at least once, as for events). Twilio's Messages and Calls APIs take no idempotency key, so the row lock is the guard.
- **Order.** Safety alerts first (`SAFETY_TEMPLATES`: `lonework_check_in_now`, `lonework_overdue`, `lonework_escalated`, `lonework_help`, `callout_offer`; calls before their texts), then sign-in codes, then open-shift texts. Pushes put the same urgent kinds first. There are no quiet hours for texts: each template is a safety alert, something the person just asked for, or something they opted into.
- **Retries.** A failed safety text is retried after 15 s, 30 s, 60 s and 120 s (the others after 1, 2, 5 and 10 minutes), up to 5 tries. The process that saw the failure sets a timer, and the worker's sweep picks it up too. The next try's time is kept under `_retryAt` in the row's params, which are dropped once the message is sent or given up on. Giving up is reported to the error reporter.
- **Alert.** A safety text or call still unsent after `SAFETY_SMS_ALERT_S` (120 s) raises an alert from the worker's sweep (`checkOverdueSafety()`, `safety_sms_overdue()`): an error report with the organization's id and counts only, and `fh_safety_sms_overdue_alerts_total`. It alerts again when more are late, or after 15 minutes. `/readyz` warns as well (outbox channel `sms_safety`, `oldestSafetyS`), as does `fh_outbox_oldest_age_seconds{channel="sms_safety"}`.
- **Metrics.** `fh_sms_queue_to_sent_seconds` (histogram by `priority` safety/other and `kind`) and `fh_sms_sends_total` (by `priority` and `outcome`: sent, retry, gave_up), counted in the process that sent. The worker has no `/metrics`, so its sends aren't scraped. Most sends happen in the API process that queued them; the `sms_safety` backlog gauge and readiness cover the rest.

## Process model

The API runs as any number of identical processes: `WEB_CONCURRENCY` processes per container on one port (Node's cluster module, `src/server.ts`), and any number of containers behind a load balancer, all on one Postgres. Plus one or more workers (`npm run worker`). Processes share nothing in memory:

| Concern | How it works across processes |
| --- | --- |
| Domain events | Transactional outbox (above); any process or worker may deliver |
| Live notifications | Each process holds **one** `LISTEN` connection (`src/lib/listen.ts`) on `fh_notifications`. Payloads are ids only (`tenantId`, `userId`, notification `id`); the process holding the person's stream tells the browser, which refetches under its own tenant. |
| Caches (feature switches and billing state, custom-role permissions, department scope, tenant lookup by subdomain) | Short TTLs (30–60 s), and every forget is announced on `fh_cache` (`src/lib/cacheBus.ts`): every process drops its copy. Forgets made inside a transaction are announced in it, so they arrive on commit. |
| Sign-in and enquiry rate limits | `RateLimitHit` in Postgres in production, and whenever `WEB_CONCURRENCY` > 1 (`auth/rateLimit.ts`) |
| Scheduled jobs | Only the worker runs them, each under a session advisory lock (`pg_try_advisory_lock`), so one worker at a time runs each; a job still running when its next round comes is skipped |
| Sessions, tokens | Stateless JWTs and refresh tokens in Postgres |
| Uploaded files | Encrypted in Postgres (up to 10 MB each, `routes/documents.ts`); nothing is written to a process's disk, so a container can be replaced at any time. One set of rules for every upload (`lib/files.ts`): the type is read from the file's first bytes and must be PDF, PNG, JPEG or WebP (each upload narrows this: résumés PDF only, logos images only); the name is reduced to plain characters with the extension of the real type (`storedName`); files go back only as downloads with `nosniff` and `Content-Security-Policy: default-src 'none'; sandbox` (`sendFile`) |
| Cache misses at the same moment | Share one load per key (`src/lib/singleFlight.ts`); a load that raced a forget is returned but not cached |
| Heavy reads | Running reports reads from `READ_REPLICA_URL` when set, in a read-only transaction under the same row-level security (`replica()` in `src/lib/db.ts`) |

**LISTEN needs a direct connection.** `LISTEN_DATABASE_URL` (default `APP_DATABASE_URL`) must reach Postgres directly, or PgBouncer in *session* mode: a transaction-mode pooler hands the session to someone else between statements and the subscription is lost. The same holds for the worker's advisory-lock connection. Request traffic (`APP_DATABASE_URL`) can go through a transaction pooler.

**NOTIFY is fire-and-forget.** A signal sent while a process's LISTEN connection is down is lost, so the listener reconnects with backoff (1 s doubling to 30 s) and then tells every open stream to refetch and drops every cache. Nothing durable depends on NOTIFY: notifications are rows, and a browser that missed a signal still sees them on its next fetch.

**Running several processes locally.** `WEB_CONCURRENCY=2 npx tsx src/server.ts` (two processes on :4000), or two separate servers on different ports against the same database (`PORT=4000 …` and `PORT=4001 …`). See [SCALABILITY.md](SCALABILITY.md) for sizing.

### Service boundaries

FH deploys as three services:
- the API (any number of processes);
- the worker (scheduled jobs and outbox delivery);
- optionally, the Union Hub, which runs separately so its database role never reaches the main API.

It is not split further into microservices on purpose:
- Almost every action touches the same organization's people, positions, shifts and punches inside one row-level-security transaction. Splitting those apart would turn single transactions into distributed ones.
- The pieces that do need to scale independently are already separate: the API scales by adding processes, and slow side effects (emails, texts, pushes, webhooks, domain events) go through the outbox to whichever process or worker delivers them first.

Work moves to the worker or out of the request in these cases:
- **Already asynchronous:** notifications, emails, texts and calls, web push, webhooks, scheduled reports, retention, weather, trust monitors.
- **Still in the request, with a longer time limit:** pay runs (`payrollTx`, 120 s) and provider exports. A 300-person city-wide run took 7–15 s in the first load runs and 8.5 s in the latest, with 30 others running at once (SCALABILITY.md). Move them to a worker job, with the screen showing progress, when a run regularly takes more than about 30 s or the *Event loop blocked* alert ([MONITORING.md](MONITORING.md#event-loop-blocked)) points at them.
- **The scheduling assistant on long horizons:** the same rule applies.

## Routes without a sign-in

Most of `/api` needs a signed-in person. These don't (`src/app.ts`):

- **Calendar feed** (`GET /api/calendar/:tenantId/:secret.ics`, `routes/calendar.ts`): the secret in the link is the key; the API looks up its hash. Limited per feed and, for wrong links, per address; an unknown link, a disabled organization or an inactive person all look like no feed.
- **Facility kiosk** (`/api/kiosk`, `/api/kiosk/punch`, `routes/kiosk.ts`): the tablet sends its own token in `x-kiosk-token` (organization id and secret, stored hashed), not a person's session. A person is identified by employee number and PIN; wrong PINs lock the number (5 in 15 minutes, doubling) and pause the tablet (15 in 15 minutes); see Brute-force and credential stuffing. Revoking a kiosk stops it at once.
- **Job applications** (`POST /api/public/jobs/:id/apply`, `routes/applications.ts`): on the organization's subdomain, for postings that take applications in the app, with the same bot checks and rate limits as public sign-up.

- **Public API** (`/api/v1`, `routes/publicApi.ts`): an organization's API key (`Authorization: Bearer fh_live_…`, stored as a SHA-256), never a person's session; the organization comes from the key, and every request runs under its RLS context. Scoped (reads by default; opt-in write scopes go through the app's own services, `routes/publicApiWrite.ts`, with the key as the audit actor, Idempotency-Key and If-Match), rate-limited per key (`X-RateLimit-*` headers) and on failed keys per address, every request audited. `GET /api/v1/openapi.json` needs no key. See [PUBLIC-API.md](PUBLIC-API.md).
- **Health and metrics** (`/healthz`, `/readyz`; `/metrics` only with `METRICS_TOKEN`) and browser error reports; see below.

They sit beside the older public routes: the city logo, the careers page, public sign-up and the sign-in routes.

## Brute-force and credential stuffing

Four layers, from the edge in. Defaults are constants in code (`auth/bruteForce.ts` `POLICIES`, `routes/kiosk.ts` `KIOSK_LIMITS`, `routes/publicApi.ts` `KEY_FAILURES`) or environment variables where noted; tune them with real traffic.

| Layer | What it counts | Default | Answer |
| --- | --- | --- | --- |
| AWS WAF (`ops/terraform/edge.tf`) | Requests per address across the fleet, IP reputation, bad inputs | See the Terraform | 403/429 from the load balancer |
| Per-address token bucket (`lib/ipRateLimit.ts`, every API process, in memory) | Every request except `/healthz`, `/readyz`, `/metrics`. With a credential (Bearer token or API key, `fc_refresh`/`fh_platform`/`fh_kiosk`/`fh_support` cookie, `x-kiosk-token`, a calendar or unsubscribe link, a Stripe signature): `GLOBAL_RATE_LIMIT_AUTH`; without: `GLOBAL_RATE_LIMIT_ANON`. Each 401 also spends `GLOBAL_RATE_LIMIT_FAILURES`; when that is empty, credentialed requests from the address wait too (a made-up token doesn't buy the bigger bucket). The live notification stream is one request per connection | 1200 / 120 / 120 a minute; on in production (`GLOBAL_RATE_LIMIT=on/off` overrides; off in development and tests) | `429 RATE_LIMITED`, `Retry-After` in seconds |
| Per-route limits (`auth/rateLimit.ts`, Postgres in production) | Sign-in 20 per address and organization per 10 min; Dev console 10 per address per 10 min; passkey options and answers 30 per 10 min; forgot 5 per address and 3 per email; reset 10; password change 10 per person per 15 min; support codes, SSO, MFA codes, kiosk pairing, sign-up, enquiries as before | | `429 TOO_MANY_ATTEMPTS` |
| Per account and per address across accounts (`auth/bruteForce.ts`) | See below | | Same answer as a wrong password |

**Organization sign-in** (`POST /api/auth/login`). Per account, from any address: 5 wrong passwords (forgotten after 24 h without one) lock it for 15 minutes; each further lock within 24 h of the last doubles it (30 min, 1 h … up to 24 h). A successful sign-in (password, passkey) or a password reset starts over (`User.failedLoginCount`, `lastFailedLoginAt`, `lockoutLevel`, `lastLockedAt`, `lockedUntil`). Per address: failing on 10 different accounts (unknown emails count; the account is kept only as a hash in `RateLimitHit`) within 15 minutes blocks that address from password sign-in for 1 hour, everywhere (`auth.ip_blocked` in the organization's audit log). A lock is audited (`auth.account_locked`) and emails the person once (`account_locked`, EN/FR, transactional: the time, until when, a link to reset, "if this wasn't you"). Passkey and SSO sign-in still work during a lock, so an attacker can't keep someone out of an account they hold a passkey for.

**Dev console** (`POST /api/platform/auth/login`): stricter. 3 wrong passwords lock for 30 minutes, doubling to 24 h; 3 different emails from one address block it for an hour. Locks and blocks go to `PlatformAudit` and page on-call (`DevConsoleSignInAttack`, [MONITORING.md](MONITORING.md)); the console's admins have no tenant outbox, so there's no lock email.

**Nothing tells accounts apart.** An unknown email, a wrong password, a locked account (even with the right password) and an inactive one all answer `401 INVALID_CREDENTIALS` with the same body, after the same scrypt check (a dummy hash for unknown emails). In a closed or SSO-only organization an administrator with a wrong password gets the organization's answer, like everyone else. `POST /api/auth/forgot` always answers 202 and never in less than 150 ms. Invitations and resets share one token check (`/auth/reset`) that says only "expired or used". Passkey sign-in uses discoverable credentials (no email asked), and SSO discovery is per organization, not per email.

**Kiosk PINs** (`POST /api/kiosk/punch`). PINs are 4 to 6 digits, scrypt-hashed; common ones, one digit repeated, runs up or down (2345, 98765), repeated pairs or triples and the end of the person's own employee number are refused (`PIN_WEAK`). Only wrong PINs count: 5 in 15 minutes lock that employee number for 15 minutes, doubling with each lock that day (up to 24 h); 15 wrong PINs on one tablet in 15 minutes (someone walking through numbers) pause the tablet for 15 minutes; all punches 240 per tablet per 15 minutes (a shift change fits). Unknown numbers get the same answer and the same scrypt work. Each lock is audited and tells the people who review punches (`kiosk_pin_locked`, `kiosk_tablet_locked`, in-app). With 5 tries per lock and doubling locks, a 4-digit PIN takes on the order of months to guess, not days; 6 digits is the stronger choice (owner decision).

**Secrets and their checks.** Every bearer secret comes from `crypto.randomBytes` and only its SHA-256 is stored, so a check is a lookup by hash (there is no secret-by-secret comparison for timing to reveal): reset and invitation links (32 bytes, 1 h / 7 days, one use), refresh tokens (32 bytes), calendar feeds and support codes (24 bytes), kiosk secrets (24 bytes), API keys (43 random characters). Sign-in codes are 6 digits from `crypto.randomInt`, stored as an HMAC and compared with `timingSafeEqual`, 5 tries per code; the metrics token is compared with `timingSafeEqual`.

**Public API keys.** Per key: `rateLimitPerMinute` (120 by default, set per key) and 60 writes a minute; every answer carries `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` (seconds until a slot frees), and a 429 carries `Retry-After` with the same number. Per address: 20 failed key checks (missing, unknown, revoked, expired) in 10 minutes and the address gets `429` before any lookup, for the rest of the window.

**Calendar feeds**: 60 fetches an hour per feed, and 30 wrong links an hour per address (calendar services fetch many people's feeds from a few shared addresses, so working links aren't limited by address).

**Breached passwords (optional, off).** `PASSWORD_BREACH_CHECK=on` checks new passwords (reset, invitation, change) against Have I Been Pwned's Pwned Passwords range API (`auth/breachedPasswords.ts`): only the first 5 hex characters of the password's SHA-1 leave the server, with `Add-Padding: true`; the match is made here; 2 s timeout; any failure lets the password through. Refused: `400 PASSWORD_BREACHED`. Turning it on makes `api.pwnedpasswords.com` (served through Cloudflare) a service the API calls, so the egress allow list and the subprocessor list need it; the owner decides ([SECURITY-LEGAL-AUDIT.md](SECURITY-LEGAL-AUDIT.md)).

**Metrics and alerts**: `fh_auth_failures_total{surface,reason}`, `fh_auth_lockouts_total`, `fh_auth_ip_blocks_total`, `fh_kiosk_pin_locks_total{scope}`, `fh_api_key_auth_failures_total`, `fh_rate_limited_total{layer}`; alert rules in `ops/monitoring/alerts.yml`, runbook in [MONITORING.md](MONITORING.md#sign-in-failures-spike).

## Background worker

`npm run worker --workspace apps/api` (`src/worker.ts`) runs each job under a Postgres advisory lock, so several worker processes never run the same job at once. Every 5 seconds: domain events their API process didn't deliver (see Events), then the webhook deliveries they queued and retries that are due. Also every 5 seconds, and on each `fh_urgent` NOTIFY: urgent texts, calls and pushes, plus the overdue-safety alert (see Urgent texts, calls and pushes). Every minute: working-alone escalation, call-out timeouts, rotation alerts, shift bid rounds (open notices, closes), and the backstop delivery of email, texts and calls (`deliverSms`: Twilio, or logged when `SMS_PROVIDER=console`; up to 5 tries) and web push. Texts and calls queued by a minute job go out straight after that job's commit. Every hour: reminders, anonymization, retention, weekly shift templates' automatic drafts (only where the organization turned them on), scheduled reports (`services/reports/scheduled.ts`: each saved report is run with its owner's access at that moment and emailed weekly or monthly; someone who lost access stops getting it), benchmarks, and the weather for each distinct forecast site once its `WEATHER_REFRESH_HOURS` (3) have passed (`WEATHER=off` turns it off), Trust reminders and pruning. Every 5 minutes: the Trust tests that are due, an hourly posture snapshot and Trust alert emails ([TRUST-CENTER.md](TRUST-CENTER.md)). Each job's last start, success and failure are kept in `WorkerJobRun`.

## Health, metrics and errors

All in `routes/observability.ts` and `lib/` (`health.ts`, `metrics.ts`, `requestContext.ts`, `errorReporter.ts`, `scrub.ts`). Settings are in `apps/api/.env.example`.

- **`GET /healthz`** (liveness): answers `{ ok: true }` without touching anything. Use it for "restart the container if this stops answering"; the AWS load balancer checks it (`ops/terraform/edge.tf`).
- **`GET /readyz`** (readiness): runs `SELECT 1` within `READY_DB_TIMEOUT_MS` (1.5 s), then reads the email, text and domain-event outbox backlog (`outbox_backlog()` in `db/rls.sql`: counts and the oldest age across organizations, nothing else) and the worker's heartbeat. 200 when ready, 503 with each failing check's reason otherwise. A database that is down or slow always fails it. An outbox older than `READY_OUTBOX_MAX_AGE_S` (15 min) or a worker silent for `READY_WORKER_MAX_AGE_S` (5 min) shows as `warn` and fails only in strict mode (`READY_STRICT=on`, or `/readyz?strict=1`), so a load balancer doesn't take every API server out of service when only the worker is down. Point the load balancer at `/readyz` and an uptime alert at `/readyz?strict=1`. The body names checks, counts and ages only: no hosts, errors or organization data.
- **Worker heartbeat:** the worker is its own process with no HTTP port. After each minute's round of jobs it sets its database connection's `application_name` to `fh-worker beat=<unix seconds>`; readiness and metrics read the newest beat from `pg_stat_activity`. No table, and the beat disappears when the worker stops. The worker's lock connection must go straight to Postgres, not through PgBouncer in transaction mode (its advisory locks need that already).
- **Request ids:** every request gets an id, or keeps an incoming `X-Request-Id` made of 8–128 letters, digits and `._:-`. It's sent back in the `X-Request-Id` header and in every error body (`requestId`), and every console line logged while handling the request starts with `[req <id>]`. Ask a person for the id on the error, then search the logs and error reports for it.
- **`GET /metrics`** (Prometheus text format): only with `Authorization: Bearer <METRICS_TOKEN>`; without the setting it answers 404. Requests and latency (`fh_http_requests_total`, `fh_http_request_duration_seconds`) by method, route *pattern* (`/api/users/:id`, never the URL, so no ids reach the metrics store and series stay bounded; anything no route matched is `unmatched`) and status class; `fh_errors_total` by source; `fh_db_query_duration_seconds` (Prisma query events, on only when metrics are); memory, uptime and event-loop delay; `fh_outbox_pending`, `fh_outbox_failed`, `fh_outbox_oldest_age_seconds` by channel; `fh_worker_connected` and `fh_worker_heartbeat_age_seconds`. Numbers are per process: with `WEB_CONCURRENCY` > 1 a scrape reaches one of the container's processes, so prefer scaling out with one process per container where metrics matter.
- **Error reports** (`lib/errorReporter.ts`): the Express error handler (500s), unhandled rejections, uncaught exceptions (reported, then the process exits for its supervisor to restart), background job failures and notification fan-out failures. Each is logged as before and, when `SENTRY_DSN` is set, sent as one Sentry envelope over `fetch` (Sentry or GlitchTip; no SDK); the DSN's host must be on the public internet (`lib/egress.ts`). A report holds the error's type, first message line and stack frames, the request id, the route pattern, the organization's id and a one-way hash of the user's id; never bodies, query strings, headers, names or emails. Text goes through `lib/scrub.ts` first (emails, SIN-like, card and phone numbers, JWTs and long tokens, passwords, Authorization and cookie values). Identical errors go out at most once a minute, with a count of repeats, and no more than 60 reports a minute in all. Use a service hosted in Canada; it's an optional subprocessor ([SUBPROCESSORS.md](SUBPROCESSORS.md)).
- **Browser errors** (`apps/web/src/lib/errorReporting.ts`): uncaught errors, unhandled rejections and the page error boundary (`app/error.tsx`, which shows the usual "Something went wrong" notice with "Try again") post to `POST /api/client-errors`: the error's name, message and stack, the page path with ids replaced, and the build (`NEXT_PUBLIC_RELEASE` at build time). Never form contents, query strings or tokens. Ten reports per page load at most; the API takes 20 a minute per address and scrubs them like its own.

## Union Hub access

Access follows union membership, not employer roles: `/api/me` grants `union.hub` to union members while the organization has the hub switched on, and every hub query re-checks membership of the local through the separate `flexcity_union` database role.

### Running the hub as its own service

By default the API serves `/api/union/*` itself. For stronger separation, run it on its own:

1. Deploy the API with `UNION_HUB_MODE=separate` and **without** `UNION_DATABASE_URL` (the API refuses
   to start if it's given both). It then answers `/api/union/*` with `404 UNION_ELSEWHERE` and holds no
   way into the `union_hub` schema, so a flaw or a leaked secret in the main API can't reach union data.
2. Deploy the same build a second time as the Union Hub service: `npm run start:union --workspace apps/api`
   (`src/unionServer.ts`, port `UNION_PORT`, default 4100) with `UNION_DATABASE_URL` (the
   `flexcity_union` role), `APP_DATABASE_URL`, `JWT_SECRET` and the KMS settings. It answers only
   `/api/union/*` and `/healthz`; every other path is a 404.
3. Route `/api/union/*` to it at the load balancer (path rule above the general `/api/*` rule), or,
   for single-host set-ups, set `UNION_URL` for the web app so its rewrite sends those paths there.
   Same origin either way: no CORS, and the browser keeps one session.

The hub service checks sign-ins exactly like the API (same tokens, account still active, organization
open, signed agreement, support visits refused), reading those through the app role, which can't read
the union schema. Give the two services separate secrets stores so each holds only its own credentials.
Locally: `npm run dev:union --workspace apps/api` beside `npm run dev`.

## Feature switches

Each organization has a switch per feature (`messaging` and `surveys` among them) (`src/services/platform/features.ts`), set from the Dev console. The one exception is `seniority`, which the organization can also set in Settings (`/settings/seniority`). Text alerts (`textAlerts`) are off by default because messages cost money. A switched-off feature removes its permissions for everyone in that organization when the access token is checked, so menus hide it and permission checks refuse it; features without their own permission (lessons, union hub, public job page) also have a route guard. Notification emails follow their own switch; invitations and password resets always send.

## Menus per role

Menus are driven by permissions, never role names (`apps/web/src/lib/nav.ts`). Two permissions exist only to shape menus: `shifts.self` (works shifts: Today, My schedule) and `lessons.teach`. HR administrators and union stewards don't have them, so they don't see personal shift screens; a steward's menu is just the Union hub. `nav.test.ts` pins the menu for every role against the API's permission matrix.

## FH Dev console

FH staff (`PlatformAdmin`) are not users of any organization. They sign in at the bare FH address with an opaque, revocable session in an HTTP-only, SameSite=Strict cookie scoped to `/api/platform`; every console request must also send `x-fh-platform: 1`. Organization tokens are refused there and console sessions are refused by organization routes. The console still reads and writes an organization's data only through `withTenant`, so row-level security applies. Every change is written to `PlatformAudit` and to the organization's own audit trail (`platform.*` actions, no user as actor).

Uploaded logos (PNG, JPEG, WebP; content-checked; SVG refused) live in `TenantLogo` and are served publicly at `/api/public/logo/:tenantId?v=<hash>`. The web app always shows the FH logo and places the city's logo beside or below it.

Beyond city set-up, the console holds plans and billing (monthly, yearly or multi-year terms, per-
option prices), FH's own books, payroll tax tables, a city's in-app payroll set-up (deposit details
and bank connection), signed agreements with certificates, consented support visits, offboarding and
website enquiries, and **Trust**, FH's own security and compliance program (controls mapped to SOC 2, ISO 27001, HIPAA, PIPEDA, provincial privacy laws and Law 25; live tests; evidence; policies; risks; vendors; customer commitments; see [TRUST-CENTER.md](TRUST-CENTER.md)). Sensitive actions ask for a passkey again (`requirePlatformStepUp`).

Staff import parses CSV on the server (`staffImport.ts`), returns a row-by-row preview with problem codes the web app translates, then creates only valid rows in one transaction, optionally sending invitations.

## Passkeys and "confirm it's you"

Passkeys use WebAuthn (`@simplewebauthn`), so Windows Hello, Face ID / Touch ID, Android biometrics and security keys all work the same way. Credentials are bound to the organization's own subdomain (or the console's address) and require user verification; challenges are stored, single use and expire after five minutes. Only public keys are stored (`Passkey`, under row-level security; `PlatformPasskey`).

### Second factor for organizations

Each organization chooses which access levels need a second factor (`Tenant.mfaRoles`, HR always; Settings › Organization, "Second sign-in factor", `PUT /api/settings/mfa`). A password-only session for such a person gets `403 MFA_REQUIRED` everywhere except what it needs to give the factor (`MFA_EXEMPT` in `auth/middleware.ts`): `/api/me`, its passkeys, step-up, and the sign-in code routes. The second factor is either:

- a **passkey** (step-up, or setting up a first one), or
- a **one-time code** by email or text (`routes/mfaCodes.ts`, `services/auth/mfaCodes.ts`), unless the organization allows passkeys only (`Tenant.mfaCodes`, on by default, the same settings card). `GET /api/auth/mfa/options` lists the channels with masked destinations (`j•••@kelowna.ca`, `•••-•••-4267`): email to the account address always; a text only to a number the person confirmed (`/me/sms/verify`) while the organization has text alerts on. `POST /api/auth/mfa/code` sends 6 digits from `crypto.randomInt`, valid 10 minutes; a new code supersedes the earlier one and drops it from the outbox if it hasn't gone out. Emails (`mfa_code`, transactional) and texts (`mfa_code`, sent right after safety alerts) are queued in the outbox and delivered as soon as the transaction commits (`urgentSoon`). The `MfaCode` row (row-level security) keeps only an HMAC-SHA256 of the code keyed with the server secret and bound to the row and the person, and is deleted 30 days after it expires (`retention.ts`), long enough to look into a lockout. The outbox message holds the code only until it is sent, then its params are cleared; the email log row (recipient, template) is kept 90 days by default (`retention.ts`). `POST /api/auth/mfa/code/verify` compares in constant time; a code works once, for 10 minutes, and dies after 5 wrong tries. Limits (`auth/rateLimit.ts`): 3 sends per 15 minutes and 10 a day per person; 10 checks per 15 minutes per person and 30 per address. Only a session that still owes a second factor can send or check a code (`409 MFA_NOT_NEEDED` otherwise), so codes are not a general step-up.

Either way, success is recorded the same way: the access token gets `mfa: true` and the refresh-token family's `mfaAt` is set (`markReauthenticated(..., true)`), so the factor survives refreshes; codes are audited as `mfa.code` (`mfa.code.locked` after 5 wrong tries). Passkeys resist phishing and codes don't, which is why an organization can turn codes off. The Dev console uses passkeys only.

Access tokens carry `aat`, the time the person last proved who they are. Refreshing keeps it unchanged; a password or passkey sign-in, or a step-up, renews it. `requireRecentAuth` guards payroll export, pay rates, HR record changes, erasure and passkey changes: older than 10 minutes, the API answers `STEP_UP_REQUIRED`, the web app asks for a passkey or password, and the original request carries on.

## Crawlers and AI bots

The app is private and the website is public, so they treat crawlers differently. One list of AI crawlers, `apps/site/src/lib/aiCrawlers.json` (training crawlers, and a separate "AI search / assistants" group), feeds the website's robots.txt, the app's robots.txt (a checked copy in `apps/web/src/lib/aiCrawlers.json`, since the web image is built from `apps/web` alone) and the AWS firewall rules.

| | Search engines | AI training crawlers | AI search / assistants |
| --- | --- | --- | --- |
| Website (`apps/site`) | Indexed (robots.txt `*`, meta `index, follow`) | robots.txt `Disallow: /`; `noai, noimageai` meta and header; TDMRep (`/.well-known/tdmrep.json`, `tdm-reservation: 1`); firewall block on AWS, Vercel's AI-bot rules on Vercel | Blocked like training crawlers by default; `ALLOW_AI_ASSISTANTS` in `apps/site/src/lib/crawlers.ts` (and `waf_block_ai_assistants` in Terraform) lets them in |
| App pages (`apps/web`) | `noindex, nofollow, noarchive, nosnippet, noimageindex, noai, noimageai` (X-Robots-Tag and meta), robots.txt `Disallow: /`, except job postings and program sign-up (`/jobs`, `/signup`), which stay indexable | robots.txt `Disallow: /` everywhere, firewall block | Same as training crawlers |
| API (`apps/api`) | X-Robots-Tag noindex on every answer (`securityHeaders`) | Firewall block | Firewall block |
| Demo (GitHub Pages) | `noindex…` meta tag on every page. Its robots.txt sits under the base path, and GitHub Pages only reads one at the domain root, so the meta tag is what counts | Meta tag only | Meta tag only |

robots.txt, the meta tags and TDMRep are requests that well-behaved crawlers honour. The firewalls (`ops/terraform/edge.tf`) enforce by user agent, which a determined scraper can fake; the per-address rate limits and optional AWS Bot Control (`waf_bot_control`) cover more. The terms of use forbid scraping and AI training on the site, demo and app. Blocked counts: [MONITORING.md](MONITORING.md).
